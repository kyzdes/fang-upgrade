# FANG-9 acceptance #2 — on the streaming route the retraction must reach the
# client BEFORE the event the client reads as the end of the turn.
#
# THE DEFECT THIS RECORDS THE FIX FOR (found in the first round's patch,
# commit 8a54309, not in upstream): the driver emits `ContentComplete` the
# instant the model stops talking, and crates/openfang-api/src/routes.rs:1634
# publishes that as `event: done`. The phantom guard runs afterwards, so the
# `[Unverified]` note was pushed as a text delta AFTER `done`. A consumer that
# treats `done` as the end of the turn saw the lie and never the retraction —
# which is worse than the defect being fixed, because now it is the protocol
# lying rather than the agent.
#
# captured : 2026-08-16T11:1xZ
# repo     : fix/fang-9-phantom-write @ 79ab1cc

#            claim after the challenge, which is the ONLY path that emits the
#            note. phantom-write-claim (phase B of FANG-9.sh) ends with a real
#            file_write, so it never produces one and says nothing about order.
# routes   : POST /api/agents/{id}/message/stream  (SSE)
#            GET  /api/agents/{id}/ws              (WebSocket, hand-rolled
#            RFC6455 client — this box has no websockets/websocket-client)
#
# THE RED SIDE is not on this stand. The unpatched build has no phantom guard
# in the streaming loop at all, so it emits no note and there is nothing to
# order; the "before" is commit 8a54309, and it is reproduced as a unit test
# rather than as an image: agent_loop.rs
# `test_streaming_note_precedes_the_final_content_complete`, run against a
# tree with the gate removed, fails with
#
#     the note must reach the client before the event that ends the turn;
#     got note at 7, last ContentComplete at 5
#
# and prints the whole event vector. That is the same defect this file shows
# fixed, measured at the unit that decides it.
#

#   answer is being challenged before it is told that call is complete.

#   WS — there is no per-call `done` on this surface and there never was:
